---
title: OAuth applications
description: Connect delegated users or an installed application with exact audiences, least-privilege scopes, and revocation-safe credentials.
---

FortyOne has two OAuth actor models. Choose one intentionally:

- authorization code with S256 PKCE acts as the consenting `oauth_user` and
  remains subject to that user's current workspace, role, team, and resource
  access; or
- `client_credentials` acts as a dedicated `oauth_application` principal for
  one workspace installation approved by a current administrator.

The installer is never the application actor. Application tokens are currently
limited to idempotent story creation with `stories:write`; all reads, updates,
deletes, comments, webhook administration, and MCP access remain unavailable to
application actors.

## Discover the server

Read the authorization-server and protected-resource metadata instead of
hard-coding endpoints:

```text
GET https://api.fortyone.app/.well-known/oauth-authorization-server
GET https://api.fortyone.app/.well-known/oauth-protected-resource/mcp
GET https://api.fortyone.app/.well-known/oauth-protected-resource/api/v1
```

Choose one audience per authorization:

| Audience        | Exact production resource         | Scopes                                             |
| --------------- | --------------------------------- | -------------------------------------------------- |
| Public REST API | `https://api.fortyone.app/api/v1` | `offline_access` plus one or more API capabilities |
| Remote MCP      | `https://api.fortyone.app/mcp`    | `mcp:access offline_access`                        |

Use the exact `resource` value from the matching protected-resource metadata
throughout authorization, code exchange, and refresh. A token for MCP cannot
authenticate to `/api/v1`; an API token cannot authenticate to MCP or to an
unversioned FortyOne product route. Do not combine MCP and API scopes in one
authorization request.

The authorization-server metadata advertises both `authorization_code` and
`client_credentials`. Protected-resource metadata remains authoritative about
the exact audience. Advertising a grant type does not enable it for every
resource: application actors are enabled only for `/api/v1`, never `/mcp`.

## Register a public client

Dynamic registration supports public PKCE clients. Register one to ten exact
callbacks; wildcard and prefix callbacks are not accepted. Registration accepts
one bounded JSON object with only the fields shown below, so unsupported client
metadata must not be sent.

```sh
curl --fail-with-body \
  --request POST \
  --header 'Content-Type: application/json' \
  --data '{
    "client_name": "Example FortyOne integration",
    "redirect_uris": ["https://integration.example/oauth/callback"],
    "token_endpoint_auth_method": "none"
  }' \
  'https://api.fortyone.app/oauth/register'
```

Store the returned `client_id` and `client_id_expires_at`. Dynamic registrations
are intentionally time-bounded; register again after expiry. A client ID is
metadata, not a secret.

## Create and install a confidential application

Managed confidential applications are separate from dynamic public clients.
A current workspace admin creates the application in FortyOne's integration
settings and receives its initial client secret exactly once. Store that value
directly in a secret manager; later lists show only the non-secret prefix and
lifecycle timestamps.

An admin then installs the application's `client_id` into a workspace for the
exact resource:

```text
resource=https://api.fortyone.app/api/v1
scopes=stories:write
```

The installation response provides an `id`; use that installation UUID in each
client-credentials exchange. It is also the stable rate-limit and idempotency
identity. The separate `principalId` is immutable action attribution. Neither
value is the installer user ID, and the access-token `jti` must not replace
either one.

Management requires an authenticated human workspace admin with
`integrations:manage`. The first-party settings API exposes create/list,
show-once rotation, secret revocation, install/list/update, and installation
revocation under `/workspaces/{workspaceSlug}/oauth-applications` and
`/workspaces/{workspaceSlug}/oauth-application-installations`. These are
administrator session routes, not public bearer integration endpoints.

Secret rotation requires `overlapSeconds` from 60 through 86,400. During that
window both generations may exchange tokens; the old generation stops at the
earlier of its normal expiry or `previousSecretOverlapExpiresAt` in the
rotation response. Revoke the old secret after every running integration has
adopted the replacement. Revoking the installation disables its dedicated
principal and invalidates already-issued application tokens on their next API
verification.

## Choose API scopes

The `/api/v1` OAuth audience supports:

```text
offline_access
workspaces:read
teams:read
stories:read
stories:write
comments:read
labels:read
sprints:read
objectives:read
webhooks:manage
```

Every API grant includes `offline_access` and must request at least one API
capability. Ask only for operations your client uses. Some routes combine
capabilities: comment reads require both `comments:read` and `stories:read`;
workflow-state reads use `stories:read`; and key-result reads use
`objectives:read`. Scopes only allow an operation to be requested. They do not
create workspace membership, administrator status, team access, or resource
visibility.

## Authorize with S256 PKCE

Generate a 43-128 character verifier from the RFC unreserved character set.
Set `code_challenge` to the unpadded base64url SHA-256 digest of that verifier.
Open `/oauth/authorize` with:

- `response_type=code`;
- your `client_id` and exact `redirect_uri`;
- an unpredictable client-side `state` value;
- `code_challenge_method=S256` and the challenge;
- the exact selected `resource`; and
- only scopes supported by that resource.

For a public-API client that reads stories, use:

```text
resource=https://api.fortyone.app/api/v1
scope=offline_access stories:read
```

For a remote MCP client, use:

```text
resource=https://api.fortyone.app/mcp
scope=mcp:access offline_access
```

Verify `state` and `iss` on the callback before exchanging the code. Never put
the verifier, code, access token, or refresh token in logs or analytics.

## Exchange and rotate delegated tokens

Send form values in the bounded POST body, never in the query string:

```sh
curl --fail-with-body \
  --request POST \
  --header 'Content-Type: application/x-www-form-urlencoded' \
  --data-urlencode 'grant_type=authorization_code' \
  --data-urlencode 'client_id=<client id>' \
  --data-urlencode 'redirect_uri=https://integration.example/oauth/callback' \
  --data-urlencode 'code=<one-time code>' \
  --data-urlencode 'code_verifier=<original verifier>' \
  --data-urlencode 'resource=https://api.fortyone.app/api/v1' \
  'https://api.fortyone.app/oauth/token'
```

Access tokens expire after 15 minutes. Every refresh exchange returns a new
refresh token; replace the stored value atomically before making another
refresh request. Reusing a consumed generation revokes the complete family and
requires authorization again.

Revoke a connection with a form-encoded `token` at `/oauth/revoke`. The endpoint
returns success even for an unknown token so callers cannot probe credential
existence.

Send an API-audience access token as the single bearer header on `/api/v1`:

```http
Authorization: Bearer <access token>
```

Do not send an MCP-audience token to that route group. FortyOne verifies the
audience, active application, grant, user, and granted scopes before selecting
the requested workspace and rechecking current membership.

## Exchange an installed application credential

Authenticate the client with exactly one `Authorization: Basic` header. Send
the installation, resource, and scope in the form body:

```sh
curl --fail-with-body \
  --request POST \
  --user '<client id>:<client secret>' \
  --header 'Content-Type: application/x-www-form-urlencoded' \
  --data-urlencode 'grant_type=client_credentials' \
  --data-urlencode 'installation_id=<installation UUID>' \
  --data-urlencode 'resource=https://api.fortyone.app/api/v1' \
  --data-urlencode 'scope=stories:write' \
  'https://api.fortyone.app/oauth/token'
```

Do not send `client_id` or `client_secret` in the body or query string; FortyOne
rejects alternate secret channels with `invalid_client`. The installation UUID,
resource, and scope are required and exact. The requested scopes must be a
subset of the currently installed scopes.

The response contains a 15-minute bearer access token and no refresh token.
Request a new token when needed. Send it to the idempotent story-create route
with a durable logical-operation key:

```http
POST /api/v1/workspaces/<installed workspace UUID>/stories
Authorization: Bearer <application access token>
Idempotency-Key: <16-255 byte stable retry key>
Content-Type: application/json
```

The path workspace must equal the installed workspace. A newly exchanged token
cannot bypass an existing idempotency receipt because receipts use the stable
installation UUID, not the token `jti`. An application token returns
`principal_not_supported` for every currently unreleased application operation.

## When OAuth is not the right credential

- Use a personal access token for a personal script or a simple user-owned
  integration that does not need a redirect and consent flow.
- Use a service-account key for workspace-owned automation where the documented
  operation accepts a non-human actor. The current preview supports service
  accounts for idempotent story creation.
- Use delegated OAuth for a third-party application that connects as each
  consenting user and may need access to more than one of that user's
  workspaces.
- Use an installed OAuth application when a third-party backend needs the
  released workspace-owned story-create capability without a user session.

A dynamic public `client_id` is metadata only. A managed confidential
application becomes an actor only through an active admin-approved installation
and a successful client-credentials exchange.

## Client safety checklist

- Keep `state`, verifier, code, and tokens out of URLs except the standards-
  required authorization callback code/state.
- Encrypt refresh tokens at rest and serialize refreshes per connection.
- Treat `invalid_grant` during refresh as reauthorization, not an infinite retry.
- Validate TLS, set an HTTP timeout, and never follow an OAuth redirect to an
  unregistered destination.
- Preserve user attribution: this grant is an `oauth_user`, not an application
  actor or the identity of the developer who registered the client. Preserve
  installation-principal attribution for `oauth_application`; never substitute
  the installer.
- Keep client secrets in a secret manager, rotate with the shortest practical
  bounded overlap, and revoke the installation if application access is no
  longer trusted.
- Respect `RateLimit-*` and `Retry-After` response headers. Retry with bounded
  exponential backoff and jitter; never loop immediately on `429` or `503`.
