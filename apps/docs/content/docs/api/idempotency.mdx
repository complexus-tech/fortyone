---
title: Idempotent writes
description: Retry supported FortyOne mutations without creating duplicate resources.
---

An idempotency key identifies one logical mutation. FortyOne currently requires
one for `POST /api/v1/workspaces/{workspaceId}/stories`. If a connection closes
before you receive the response, resend the **same request body bytes** with the
**same key**. FortyOne either returns the completed result or prevents a second
copy from being created.

## Generate and retain one key

Generate a cryptographically random key once, before the first attempt. Keep it
with the pending operation until you have a final response. A new key means a
new logical operation, so generating a key inside a retry loop defeats the
protection.

Keys must contain 16–255 visible ASCII characters (`!` through `~`), with no
spaces or line breaks. The Go and TypeScript SDK helpers return 64-character
random hexadecimal keys that satisfy this contract:

```go
key, err := fortyone.NewIdempotencyKey()
if err != nil {
    return err
}
```

```ts
import { createIdempotencyKey } from "@fortyone/sdk";

const key = createIdempotencyKey();
```

Do not derive a key from the title, user email, current time, or another
guessable value. The key is not an authentication secret, but it should still
stay out of URLs and logs.

## Exact request bytes matter

FortyOne hashes the exact bounded JSON bytes received by the endpoint. JSON
that represents the same object can still be different at the byte level:

```json
{
  "title": "Investigate latency",
  "teamId": "7ec30f3e-915c-45de-b0f2-e4c62b876949"
}
```

is different from:

```json
{
  "teamId": "7ec30f3e-915c-45de-b0f2-e4c62b876949",
  "title": "Investigate latency"
}
```

Serialize the body once and retain those bytes, or use the same deterministic
serializer and unchanged input on every attempt. Do not add an optional field,
change whitespace, reorder object members, or change a value while retaining
the key. FortyOne never stores the raw key or request body; it stores
fixed-length digests and the safe replay result.

The key is scoped to the authenticated principal, workspace, HTTP method, and
operation. It does not grant access and does not replace the `stories:write`
scope, current credential state, workspace binding, or team authorization.

## Create a story with cURL

This preview operation accepts a personal access token (PAT), service-account
key, or user-authorized OAuth token with `stories:write`. The OAuth token must
target the exact `https://api.fortyone.app/api/v1` resource. A service-account
key is the preferred workspace-owned writer credential because it preserves
machine attribution and can be restricted to the target team; OAuth preserves
the consenting user's attribution and current product authorization.

```sh
export FORTYONE_IDEMPOTENCY_KEY="$(openssl rand -hex 32)"
FORTYONE_STORY_BODY="$(printf \
  '{"title":"Investigate latency","teamId":"%s"}' \
  "${FORTYONE_TEAM_ID}")"

curl --fail-with-body \
  --request POST \
  --header "Authorization: Bearer ${FORTYONE_WRITE_TOKEN:-${FORTYONE_TOKEN}}" \
  --header "Content-Type: application/json" \
  --header "Idempotency-Key: ${FORTYONE_IDEMPOTENCY_KEY}" \
  --data-binary "${FORTYONE_STORY_BODY}" \
  "https://api.fortyone.app/api/v1/workspaces/${FORTYONE_WORKSPACE_ID}/stories"
```

For a production integration, persist the key and serialized body before the
first network attempt. A shell variable is only suitable for this one-session
example.

## Response states and retry decisions

| Result                                       | Meaning                                                                 | Client action                                                                                                  |
| -------------------------------------------- | ----------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `201 Created`                                | The story was created, or the completed result was replayed.            | Record the returned story and stop retrying.                                                                   |
| `409` + `idempotency_in_progress`            | An identical attempt still owns the operation lease.                    | Wait for `Retry-After`, then resend the exact body and key.                                                    |
| `409` + `idempotency_key_reused`             | The key is still active but the request bytes differ.                   | Do not retry that combination. Recover the original bytes, or use a new key only for a genuinely new mutation. |
| `429 Too Many Requests`                      | The credential exceeded its rate budget before the mutation ran.        | Wait for `Retry-After`, then resend the exact body and key.                                                    |
| `503 Service Unavailable` with `Retry-After` | Receipt or rate-limit coordination could not safely finish the attempt. | Wait as instructed, then resend the exact body and key.                                                        |
| `5xx` without `Retry-After`                  | The endpoint returned a terminal safe response for this operation.      | Surface the error; do not turn it into an automatic retry loop.                                                |
| Network timeout or disconnect                | The client cannot know whether the server committed the story.          | Treat the outcome as unknown; resend the exact body and key.                                                   |

Authentication, media-type, body-size, and schema checks can reject a request
before an idempotency receipt begins. Fix those errors rather than retrying
them unchanged. Branch on the stable error `code`, not its human-readable
message.

FortyOne's current exact-body receipt retention is 24 hours after completion.
The story also has a separate durable creation identity that continues mapping
the key to the original story after the receipt expires. Persist the key for at
least the full retry lifecycle and never deliberately recycle it or depend on
expiry to create another story. This durable identity is what lets recovery
after a server crash converge on the original story instead of inserting a
duplicate.

## Safe retry loop

1. Build and serialize the request once.
2. Generate one key and durably store the key plus serialized bytes.
3. Send the request with an explicit timeout.
4. On `201`, store the result and mark the operation complete.
5. On `idempotency_in_progress`, `429`, or a `503` carrying `Retry-After`, honor
   `Retry-After` and use bounded exponential backoff with jitter.
6. On a network failure, retry with the same key and bytes.
7. On `idempotency_key_reused` or a deterministic `4xx`, stop and surface the
   error for correction.

The SDK transports never retry writes automatically. Your integration owns the
durable key, request bytes, retry budget, and recovery decision.
