The FortyOne developer API is a separate, versioned surface for integrations.
The current preview exposes workspace, team, story, and outbound-webhook
contracts. Existing web-application endpoints are not part of this contract.

## Before you begin

For a personal script, create a personal access token in workspace developer
settings with an expiry and only the scopes your integration needs. The token
is shown once, so put it directly in a secret manager. A third-party client can
instead complete the [OAuth authorization-code flow](./oauth-apps) for the exact
`https://api.fortyone.app/api/v1` resource. In either case, you also need the
UUID of a workspace the user can currently access.

Set local shell variables without writing the token into source code:

```sh
export FORTYONE_TOKEN='<personal access token or API-audience OAuth access token>'
# Optional least-privilege writer used only for story creation.
export FORTYONE_WRITE_TOKEN='<show-once service-account key>'
export FORTYONE_WORKSPACE_ID='<workspace UUID>'
export FORTYONE_TEAM_ID='<team UUID>'
```

Read the workspace:

```sh
curl --fail-with-body \
  --header "Authorization: Bearer ${FORTYONE_TOKEN}" \
  --header "Accept: application/json" \
  "https://api.fortyone.app/api/v1/workspaces/${FORTYONE_WORKSPACE_ID}"
```

A successful response has a typed `data` object:

```json
{
  "data": {
    "id": "8cc8aeb1-35c1-49dd-88bb-8ca16980ad77",
    "slug": "product",
    "name": "Product",
    "color": "#5b5bd6",
    "active": true,
    "role": "admin",
    "createdAt": "2026-08-01T10:00:00Z",
    "updatedAt": "2026-08-20T08:30:00Z"
  }
}
```

Keep the response `X-Request-ID` when diagnosing a failed request. Honor
`RateLimit`, `RateLimit-Policy`, and `Retry-After` rather than retrying in a
tight loop.

## Create your first story safely

Create one random idempotency key and retain it with the request. If the client
times out, retry with the same key and the exact same JSON bytes:

```sh
export FORTYONE_IDEMPOTENCY_KEY="$(openssl rand -hex 32)"
FORTYONE_STORY_BODY="$(printf \
  '{"title":"My first API story","teamId":"%s"}' \
  "${FORTYONE_TEAM_ID}")"

curl --fail-with-body \
  --request POST \
  --header "Authorization: Bearer ${FORTYONE_WRITE_TOKEN:-${FORTYONE_TOKEN}}" \
  --header "Content-Type: application/json" \
  --header "Idempotency-Key: ${FORTYONE_IDEMPOTENCY_KEY}" \
  --data-binary "${FORTYONE_STORY_BODY}" \
  "https://api.fortyone.app/api/v1/workspaces/${FORTYONE_WORKSPACE_ID}/stories"
```

This write accepts a PAT, service-account key, or API-audience OAuth token with
`stories:write`. For workspace-owned automation, create a service account in
workspace Developer settings, issue a key restricted to the target team, and
use that show-once key as `FORTYONE_WRITE_TOKEN`. For delegated third-party
access, keep using the OAuth token so the user remains the actor. The SDKs
provide `NewIdempotencyKey` for Go and `createIdempotencyKey` for TypeScript,
but your integration must persist the key and request until the retry lifecycle
ends. See
[Idempotent writes](./idempotency) for the exact-byte rule and `409` recovery
states.

Prefer a contract-generated client when working from this repository. The
[TypeScript and Go SDK previews](./sdks) add secure transport defaults, typed
pagination, typed story creation, and cryptographically secure idempotency-key
helpers without expanding the published API surface.

## Production checklist

- Give each integration its own short-lived credential and minimum scopes.
- Keep the bearer token out of URLs, logs, analytics, source code, and browser storage.
- Set an explicit HTTP timeout and retry only reads or mutations with a documented idempotency contract.
- Persist one key and the exact serialized body before attempting an idempotent mutation.
- Treat cursors as opaque strings and start from the first page if one expires.
- Pin your client to `/api/v1`; do not call unversioned application routes.
