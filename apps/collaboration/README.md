# Document collaboration

Self-hosted Tiptap + Yjs + Hocuspocus, with PostgreSQL persistence and no paid service dependency. The Go API provides document-scoped session tokens, permissions, history, restoration, and public sharing. This service synchronizes title/body edits, carets, and presence.

## Deploy document collaboration and Maya

Document Maya answers run through the existing Go worker. Document edits require this collaboration service as the authoritative Yjs writer; there is no separate comments feature flag.

1. Apply migrations through **228** using the normal migration process before deploying the updated API, worker, or collaboration service. Migration 227 adds the durable agent-edit queue, consumer readiness, body mention/reference indexes and synchronization functions. Migration 228 keeps body mention observations independent from current recipient access so sharing does not re-notify unchanged mentions. Existing collaboration/history migrations remain required.
2. Deploy the updated Go API, worker, and Projects app together. Keep the existing Maya model configuration. Answers are available independently of collaborative editing; document edits are offered only while a healthy consumer is present and the document already has initialized collaborative state.
3. Run the collaboration service using the existing database and allowed-origin settings below. The consumer publishes a database readiness heartbeat every 15 seconds, expiring after 45 seconds. It starts with the service and processes a bounded queue; no separate consumer process or new secret is needed.
4. Set the existing Projects `NEXT_PUBLIC_COLLABORATION_URL` to the reachable WebSocket endpoint and restart/redeploy Projects. A normal authenticated editor connection initializes each legacy document once. Maya never initializes a legacy document or resets its collaboration epoch; without that connection, legacy documents remain answer-only for Maya and retain their existing HTTP save behavior.
5. Verify two authenticated editors, a Maya edit from an ordinary document comment, history attribution to the requesting human, permission revocation, and reference insertion/removal before production rollout. The durable receipt is committed with the edit before the worker publishes success.

## Service configuration

1. Apply migrations through **228** and take a database backup using the normal production process. Earlier migrations add document revisions, CRDT state, scoped sessions, public tokens, and history triggers; history backfills the current version of existing documents and cannot reconstruct earlier edits.
2. Deploy the updated Go API and Projects app together. Document REST updates now require `expectedRevision`. Existing open tabs should reload. Leave `NEXT_PUBLIC_COLLABORATION_URL` unset until the collaboration service is available; version history/public links work independently.
3. Run one collaboration instance against the same database. Supply `DATABASE_URL`, `DATABASE_CA_FILE` (production), and `COLLABORATION_ALLOWED_ORIGINS`. Do not put `sslmode`, `sslcert`, `sslkey`, or `sslrootcert` in the URL: node-postgres URL SSL options can override the explicit verified CA configuration.
4. Expose port 1234 through a TLS proxy with WebSocket upgrade support. Set the proxy's idle timeout above 60 seconds and apply connection/rate limits. `/healthz` returns 200 only when PostgreSQL is reachable. Use `COLLABORATION_ALLOWED_ORIGINS=https://cloud.fortyone.app,https://*.fortyone.app` for the production workspace hosts, or an explicit comma-separated list. Only HTTPS suffix wildcards are supported.
5. Configure the Projects app's `NEXT_PUBLIC_COLLABORATION_URL=wss://<collaboration-host>` through its existing public environment mechanism, then restart/redeploy it. Verify two authenticated workspace users editing the same document and a signed-out public viewer.
6. Before scaling beyond one collaboration process (including overlapping rolling deployments), configure `COLLABORATION_REDIS_HOST`, port, password and TLS against a shared Redis instance. Redis carries synchronization/presence; PostgreSQL remains authoritative. Without Redis, use one replica and a stop/start deployment strategy.

Build from the repository root with `docker build -f apps/collaboration/Dockerfile -t fortyone-collaboration .`. The container runs as the non-root `node` user. Mount database CA files read-only and inject secrets through your deployment environment. Local development: load the existing database connection into the process environment without printing it, export `COLLABORATION_ALLOWED_ORIGINS=http://localhost:3000` (or the actual Projects origin), then run `pnpm --filter collaboration dev:collaboration` from the repository root. The non-watching command is `pnpm --filter collaboration start`. Use `NEXT_PUBLIC_COLLABORATION_URL=ws://localhost:1234` for a browser on the same local host. `.env.example` documents the variables; this service does not automatically load the Go API's `.env` file.

## Behavior and boundaries

- Accepted edits are committed before broadcast/acknowledgement. The editor shows Saved only after synchronization acknowledgement. Reconnects merge unacknowledged updates while the editing session remains valid.
- Permissions are checked for each message, again inside write transactions, and every five seconds for idle connections. Tokens expire after one hour and are refreshed on reconnect; password/session revocation is enforced through `auth_session_version`.
- Autosaves advance the conflict-detection revision, but history groups one editor’s saves into a rolling checkpoint: a new entry starts after a two-minute editing pause, ten minutes since that checkpoint began, an editor change, or a restore. Initial and restored versions are not coalesced. CRDT-only and access-only updates do not create history. Migration 195 consolidates legacy autosaves and retains at most ten checkpoints per document, pruning the oldest in the same transaction. Media referenced by retained history remains accessible.
- Restore creates a new version and advances the document's collaboration epoch. Existing editors pause and must reload; stale/offline updates cannot undo the restore. There is no offline browser persistence: copy unsaved text before closing a disconnected editor.
- Once collaboration is activated on a document, legacy HTML writes are fenced in both API and database. Do not disable the service as a rollback without a deliberate state migration: activated documents become read-only when collaboration is unavailable.
- Maya edits are bounded title changes, unique text replacements, and appended paragraphs. They preserve Yjs structure, formatted links, media, human mention atoms, and related-work atoms. Every command rechecks the source request, immutable proposal, approval where required, current document access and Maya entitlement, revision, and epoch inside one transaction; stale commands fail without changing the document. The queue receipt makes retries idempotent. Pending commands expire after 15 minutes under the same locks. Connected rooms receive committed state through Hocuspocus's normal update path; bounded catch-up also recovers a commit-before-broadcast interruption.
- Body references synchronize related work transactionally. Removing the final inline occurrence removes only relationships owned by the body; manually attached relationships survive. New eligible human body mentions notify once when inserted, without repeating on unrelated prose saves.
- Public links are **view only**, owner-controlled, disabled by default, and revocable. Re-enabling creates a new unguessable link. No account is required to view. They expose title/body and embedded media, not history, members, related work, or Drive attachments. Search engines receive noindex, and responses are not cached. Recipients can still copy content they have already viewed. Media redirects are signed for one minute, so an already-issued URL can remain usable briefly after revocation.
- Collaborative document state and individual updates are limited to 4 MiB. This includes accumulated CRDT metadata; a document reaching the cap requires recovery/compaction, not repeated retries. Uploaded media stays outside this state.

## Verification

- `pnpm --filter collaboration type-check`
- `pnpm --filter collaboration test`
- `TEST_DATABASE_URL=postgres://...@127.0.0.1:5432/postgres?sslmode=disable pnpm --filter collaboration test:integration`
- From `apps/server`: `TEST_DATABASE_URL=... go test -tags=integration ./internal/modules/documents/repository -count=1`

The integration harness accepts only localhost PostgreSQL, creates a random temporary database, applies all migrations, exercises real WebSocket clients, and drops only its own database. It requires the server's `.tools/bin/migrate` binary. Tests cover concurrent initial loading, simultaneous edits and durable acknowledgement, read-only writes, membership revocation, history, and stale-session rejection after restore. Agent tests exercise actual PostgreSQL transactions and two WebSocket clients, source/proposal binding, stale revisions/epochs, rollback of multi-operation failures, duplicate receipts, no-op edits, legacy-document rejection, trial/paid entitlement revocation, and recovery after a committed edit missed its initial broadcast. Body mention/reference tests cover duplicate reference removal, manual relationship preservation, and insertion-only notifications. Production deployment, TLS, Redis fanout, and authenticated browser acceptance remain deployment checks.
