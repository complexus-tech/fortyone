# Search persistence and access contract

The search module uses module-owned SQLC queries and the shared native pgx/v5
pool. It contains no handwritten Go query builder, and no SQLx adapter or
fallback exists in the production runtime.

This guide explains the security boundary, query organization, pagination
behavior, and validation rules that must remain true when search changes.

## Ownership and file layout

```text
internal/modules/search/
├── domain/
│   └── models.go         dependency-neutral result and parameter types
├── http/
│   ├── handlers.go       authenticated request handling only
│   └── params.go         strict query-string parsing
├── service/
│   ├── models.go         domain-facing search contracts
│   ├── params.go         caller-independent validation and bounds
│   └── search.go         use-case orchestration
└── repository/
    ├── queries/search.sql reviewed static SQL and SQLC annotations
    ├── sqlc/              generated code; never edit by hand
    ├── stories.go         story adapter
    ├── objectives.go      objective adapter
    ├── similar_stories.go duplicate-title adapter
    └── mapping.go         generated-row to domain mapping
```

The generated `repository/sqlc` types must not escape the repository package.
HTTP models must not enter the service or repository. Service-facing names are
aliases of the dependency-neutral domain types, so existing callers keep a
stable contract without forcing the repository to import the service layer.
These rules keep database nullability and transport compatibility from becoming
application-wide dependencies.

## Request flow

```text
authenticated HTTP request or internal tool
  -> service parameter normalization and limits
  -> repository SQLC parameter mapping
  -> tenant + actor membership predicates in PostgreSQL
  -> fail-closed generated-row mapping
  -> domain result
```

The API middleware resolves the workspace and authenticated actor. That is not
the only authorization check: every search query also proves the actor is an
active, non-system workspace member and a member of the row's team. Repository
predicates are deliberate defense in depth for HTTP, Slack, Maya, and future
integration callers.

## Tenant and actor invariants

Every story, objective, and similar-story query requires:

1. an exact `workspace_id` match;
2. a matching `workspace_members` record for the actor;
3. a matching `team_members` record for the actor and result team;
4. an active, non-system `users` record for the actor; and
5. the result team to belong to the same workspace as the result.

Story search additionally excludes soft-deleted stories. Optional assignee and
lead enrichment only exposes active, non-system users who are members of the
same workspace. A missing enrichment record remains `null`; it never causes a
cross-workspace user lookup.

Do not remove these joins because a caller currently uses workspace middleware.
Search is also called by internal tools, and repository-level scope is the last
line of defense against a confused or incorrectly wired caller.

## Static typed filters

All user-controlled values are bind parameters. The SQL text is constant and
generated by SQLC. The following filters are typed:

| Search          | Filters                                                         |
| --------------- | --------------------------------------------------------------- |
| Stories         | workspace, actor, text, team, assignee, status, priority, label |
| Objectives      | workspace, actor, text, team, status                            |
| Similar stories | workspace, actor, title, optional team, result limit            |

Ordering is selected by fixed `CASE` expressions for `relevance`, `updated`, or
`created`. User input is never concatenated into `ORDER BY`, `WHERE`, `LIMIT`,
or `OFFSET`. Every ordering ends with a stable UUID tie-breaker so equal scores
or timestamps cannot randomly reshuffle a page.

Text search combines PostgreSQL full-text search with trigram similarity for
stories. Similar-story matching normalizes titles and removes a small fixed set
of low-signal task words before comparing titles. The threshold is part of the
reviewed SQL contract, not a request parameter.

## Pagination behavior and bounds

The compatibility API currently uses page-number pagination. The service
enforces these bounds before an integer reaches SQL:

| Parameter               | Default |                Maximum |
| ----------------------- | ------: | ---------------------: |
| `page`                  |       1 |                  1,000 |
| `pageSize`              |      20 |                    100 |
| query length            |   empty | 200 Unicode characters |
| similarity result limit |       3 |                      5 |
| similarity title length |   empty | 500 Unicode characters |

The common query path uses `COUNT(*) OVER()` so the page and its total are read
from one database statement. An offset beyond the final row produces no window
row; in that case only, the repository runs a second, fully typed count query so
the API preserves the correct total instead of reporting zero.

New public v1 endpoints should follow the cursor contract in
[`../architecture/decisions/0006-cursor-pagination.md`](../architecture/decisions/0006-cursor-pagination.md).
The bounded page API remains a compatibility surface until that endpoint is
introduced.

## Projection mapping

SQLC correctly represents several legacy nullable columns as pointers. Domain
search models still require a story sequence and priority and an objective's
team, workspace, and status. `mapping.go` checks those required projections and
returns an error when they are `NULL`; it never invents an ID, sequence, status,
or priority.

This fail-closed behavior intentionally matches the safety of the previous
strict SQL scan while making the nullability visible at compile time. Optional
columns such as assignee, lead, dates, health, and labels remain optional.

## Sensitive-data observability

Search queries and proposed titles can contain customer names or unreleased
work. Logs and spans therefore record only:

- workspace and actor IDs already used for operational correlation;
- whether a query exists;
- bounded Unicode character counts; and
- returned result counts.

Never add the raw query, title, database statement, access token, or provider
payload to logs, metrics, or tracing attributes. Follow
[`../architecture/decisions/0010-observability-and-sensitive-data.md`](../architecture/decisions/0010-observability-and-sensitive-data.md).

## Changing a query

1. Change only `repository/queries/search.sql`.
2. Keep exact tenant and active-actor predicates in every new query.
3. Use `sqlc.arg` and `sqlc.narg`; do not build SQL in Go.
4. Add stable ordering and explicit pagination bounds.
5. Run `make sqlc-generate` and review every generated parameter and nullable
   result type.
6. Update the handwritten mapper without exporting a generated type.
7. Add unit coverage for validation and projection mapping.
8. Add PostgreSQL 18 integration coverage for positive access and negative
   tenant, team, and inactive-actor cases.

## Verification

From `apps/server`:

```bash
make sqlc-generate
make sqlc-check
go test -race ./internal/modules/search/...
go vet ./internal/modules/search/...
TEST_DATABASE_URL='postgresql://test-role:password@127.0.0.1:5432/postgres?sslmode=disable' \
  go test -count=1 -race -parallel=1 -tags=integration \
  ./internal/modules/search/repository
```

The integration role and database must be disposable and must satisfy the
contract in [`../testing/integration-infrastructure.md`](../testing/integration-infrastructure.md).
The test creates a unique database, applies the complete migration chain, checks
that the server is PostgreSQL 18, and drops the database during cleanup.

The integration fixture proves:

- workspace and team isolation, including deliberately inconsistent
  team-only membership;
- inactive actors receive no results;
- deleted and unjoined-team stories are absent;
- static team, priority, and label filters work together;
- page order and totals remain stable, including an empty high-offset page;
- objective search enforces the same scope; and
- duplicate-title suggestions cannot escape the actor's teams.
