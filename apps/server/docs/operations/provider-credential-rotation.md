# Provider credential KEK rotation

This runbook rotates the key-encryption key (KEK) used by retained GitHub,
Slack, and Figma OAuth credentials. It covers the in-process keyring backend and the
bounded worker maintenance operation. It does not rotate or revoke the OAuth
credential at the provider; use that provider's incident procedure when the
credential itself may have escaped.

Read the [vault security contract](../security/provider-credential-vault.md)
before operating this procedure. Migrations `000154_provider_credential_vault`
and `000169_figma_vault_installation_generation` must already be applied. Never
edit or roll back an applied migration as part of a key rotation.

## Invariants

- Every API and worker receives an identical keyring during a rotation window.
- The active key reference exists in that keyring and contains exactly 32
  independently generated bytes.
- The previous key remains available until a clean proof pass has completed
  and every ordinary process has been redeployed without needing it.
- Exactly one controlled worker enables
  `APP_CREDENTIAL_VAULT_REWRAP_ON_STARTUP`. Repeated or overlapping runs are
  cryptographically and transactionally safe, but duplicate scans add load and
  obscure the operational proof.
- Rewrap changes only the wrapped DEK and KEK reference. It preserves the
  provider ciphertext and provider generation.
- Maintenance writes use an exact compare-and-swap. Provider refresh, relink,
  reinstall, disconnect, revoke, and uninstall completion always win.
- Logs, tickets, dashboards, and terminal transcripts contain no key material,
  OAuth token, vault envelope, request body, or decrypted payload.

## Before the change

1. Assign one operator and one reviewer. Record the old key ID/version and the
   proposed new ID/version, but never the key material.
2. Confirm API and worker health, PostgreSQL headroom, a recent recoverable
   backup, and zero legacy provider credentials using the queries in the vault
   security contract.
3. Generate the new 32-byte KEK in the production secret-management workflow.
   Do not generate it in a copied shell command, local `.env`, chat, or ticket.
4. Verify staging with a synthetic old-key envelope and the exact deployment
   mechanism. Exercise decrypt, new writes, rewrap, repeat rewrap, disconnect,
   revoke, and rollback.
5. Keep `APP_CREDENTIAL_VAULT_REWRAP_ON_STARTUP=false` on every ordinary API and
   worker deployment.

## Phase 1: expand the keyring

Deploy both generations everywhere while leaving the old reference active:

```text
APP_CREDENTIAL_VAULT_ACTIVE_KEY_ID=provider-credentials
APP_CREDENTIAL_VAULT_ACTIVE_KEY_VERSION=<old-version>
APP_CREDENTIAL_VAULT_KEYS={"provider-credentials@<old-version>":"<managed-secret>","provider-credentials@<new-version>":"<managed-secret>"}
APP_CREDENTIAL_VAULT_REWRAP_ON_STARTUP=false
```

Wait for every API and worker task to be replaced and ready. An unknown-key
error at this phase means the keyring is not consistent; stop and repair it.
Do not activate or remove a key while tasks disagree.

## Phase 2: write with the new generation

Change only `APP_CREDENTIAL_VAULT_ACTIVE_KEY_VERSION` to the new version on all
ordinary API and worker tasks. Retain both entries in the keyring and keep the
rewrap flag false. Wait for the rollout to complete.

New GitHub links, Slack installations, Figma connections, and provider
refreshes now use the new KEK. Existing envelopes remain readable with the
retained previous key. Normal provider traffic may continue: the persistence
fences make a concurrent update authoritative.

## Phase 3: run one bounded rewrap

Start exactly one controlled worker with the same old+new keyring, the new key
active, and:

```text
APP_CREDENTIAL_VAULT_REWRAP_ON_STARTUP=true
```

Before it reports ready or consumes jobs, the worker:

1. completes the bounded legacy GitHub, Slack, and Figma credential backfills
   and residual plaintext/legacy-envelope scrub;
2. scans GitHub user credentials in stable UUID pages;
3. scans active Slack installations in stable UUID pages;
4. scans non-completed Slack uninstall credentials in stable UUID pages;
5. scans Figma connections in stable UUID pages; and
6. authenticates each envelope and compare-and-swap rewraps non-current DEKs.

The success logs contain only the active key ID/version and aggregate fields:
`scanned`, `current`, `rewrapped`, and `stale`. They must not contain tokens,
envelopes, key bytes, credential JSON, or raw provider errors.

If the worker exits partway through, keep both keys and restart the controlled
run. Already-current envelopes authenticate as exact no-ops. A database error
cannot turn a partial run into a plaintext or unfenced write.

## Phase 4: prove completion

Run the controlled worker again with the same configuration. The retirement
proof is:

- startup succeeds;
- `rewrapped=0`;
- `stale=0`; and
- `current=scanned` for the GitHub, Slack, and Figma reports.

`stale>0` normally means a provider lifecycle operation won its race. It is not
data loss. Rerun until a quiet proof pass has no stale writes. Investigate an
unexpected change in `scanned` against installation/link activity; do not infer
completion from an approximate row count.

Stop the controlled worker or redeploy it with the rewrap flag false. Exercise:

- GitHub user link, authenticated provider call, relink, and unlink;
- Slack install, authenticated event handling, reinstall/refresh, disconnect,
  provider revoke, and uninstall retry;
- Figma connect, authenticated design lookup, refresh, reconnect, webhook
  generation cancellation, and disconnect; and
- worker/API restarts with the new key active and both keys still present.

## Phase 5: retire the previous key

Only after the proof and smoke tests, remove the old key from the managed
keyring and replace every API and worker again. Keep the rewrap flag false.
Watch startup, vault authentication, unknown-key classifications, provider
health, and uninstall retries through the agreed observation window.

Retiring the key is the irreversible boundary for old envelopes. Keep the
secret-manager recovery version subject to the organization's access and
retention policy; do not copy the material into an application rollback file.

## Rollback

Before old-key retirement, rollback is read-safe: make the previous reference
active again while retaining both keys. New-key envelopes remain decryptable.
If policy requires all envelopes to return to the previous KEK, run one
controlled worker with the previous key active and use the same proof pass.

After old-key retirement, restore the complete old+new keyring to every process
before changing the active reference. An `unknown key` failure is not a reason
to bypass authentication, rewrite envelope metadata, or restore plaintext.
Recover the missing KEK through the managed secret workflow, rerun maintenance,
and then reassess retirement.

Never use migration down files, direct SQL envelope edits, a forced migration
version, or a provider-token copy as a rotation rollback.

## Failure handling

| Signal                            | Meaning                                                            | Required action                                                                                                                              |
| --------------------------------- | ------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Unknown key                       | A retained envelope references a KEK absent from this process      | Stop the rollout; restore and synchronize the complete keyring, then rerun.                                                                  |
| Authentication/malformed envelope | Wrong trusted binding, corrupted ciphertext, or tampering          | Preserve the row for investigation, stop automatic retries, revoke/reinstall that provider credential, and inspect safe audit metadata only. |
| Database/write failure            | The bounded scan could not persist a fenced update                 | Retain both keys and restart the idempotent controlled run after PostgreSQL recovery.                                                        |
| Stale count                       | A concurrent provider lifecycle operation won the compare-and-swap | Rerun; investigate only if a quiet proof pass continues to report stale rows.                                                                |
| Partial completion                | Some rows moved and some did not                                   | Keep both keys; restart. Never bulk-replace ciphertext with direct SQL.                                                                      |
| Suspected KEK exposure            | KEK confidentiality may be lost                                    | Rotate the KEK and assess provider-token exposure. Rewrap alone does not revoke a copied OAuth token.                                        |
| Suspected OAuth-token exposure    | A provider credential may be copied                                | Revoke/unlink/reinstall at the provider and locally. Do not treat KEK rewrap as containment.                                                 |

## Verification commands

Run the focused contract before production use:

```bash
go test -race ./internal/platform/credentialvault \
  ./internal/modules/github/repository ./internal/modules/github/service \
  ./internal/modules/slack/repository ./internal/modules/slack/service \
  ./internal/modules/figma/repository ./internal/modules/figma/service

TEST_DATABASE_URL='postgresql://<disposable-createdb-role>@<postgres-18-host>/<control-db>?sslmode=disable' \
  go test -tags=integration -count=1 \
  ./internal/modules/github/service ./internal/modules/slack/service \
  ./internal/modules/figma/repository

go test ./internal/bootstrap/architecture
make security-check
make gitleaks-check
```

The tagged suite creates isolated databases, applies the real migration chain,
and drops only those test-owned databases. It covers mixed KEK generations,
idempotent rewrap, real concurrent Slack and Figma refresh/rewrap fencing,
revoke/disconnect fencing, unknown or tampered envelopes, and active-key
rollback.
