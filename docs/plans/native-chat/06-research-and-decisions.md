# Research and decision register

## 1. Scope and evidence

Research date: **16 October 2026**. Product target: **1,000 concurrent users**, confirmed by the product owner. Repository reference: `68c1fe28f128455c9bc78c0d22574fe43f135c6f`, inspected together with current working-tree changes. The implementation has not been load-tested or deployed as part of this planning work.

The selected design is global Chat in FortyOne's navigation, with team conversations and contextual work previews. The owner's corrections are authoritative: reuse Maya's existing identity/avatar, display Maya without an AI badge, and include her naturally in the member avatar stack. Generated screenshot labels and examples do not override those instructions or existing product terminology.

Current uncommitted story-comment collaboration, attachment, notification, desktop and migration work was inspected as integration context. Its presence is not evidence that it is merged or deployed. This plan adds documentation only and does not modify those implementations, apply migrations or assign new migration numbers.

## 2. What product research supports

The opportunity is a short path from discussion to accountable work. Existing products demonstrate useful patterns: creating work from a message, linking the result back to the discussion, updating a rich card and continuing without switching context. Linear documents issue creation, agent mentions and synced discussion through its Slack integration; ClickUp documents creating or connecting tasks from chat messages. These are product precedents, not proof of adoption or return on investment for FortyOne. [Linear Slack integration](https://linear.app/docs/slack), [ClickUp chat-to-task workflow](https://help.clickup.com/hc/en-us/articles/26425806391703-Create-or-connect-tasks-from-Chat-messages)

Slack's agent guidance supports brief progress, source references, thread responses, audience-aware context and grouped updates. This plan adapts those interaction principles to native FortyOne chat. Slack-specific identity presentation, app permissions and platform retention rules are not automatically requirements for native chat. The owner’s plain Maya name and existing avatar remain the design direction. [Slack agent design](https://docs.slack.dev/concepts/agent-design/)

The plan's main product hypothesis is that users will value conversation history most when it remains connected to tickets, decisions and ownership. Test that hypothesis with a pilot before expanding into calls, large private-channel taxonomies or external chat federation.

### Pilot learning plan

Recruit a proposed three to five teams with different work patterns for a two-week pilot after the human-chat and Maya gates pass. These are suggested research parameters, not a delivery promise. Record a baseline for how those teams currently turn discussion into work, then compare equivalent workflows with Chat.

Measure active participating teams, members who both read and contribute, conversation-to-ticket completion time, generated tasks accepted/edited/rejected, duplicate tasks, reopened sources, successful cross-device continuation, notification muting and reported interruptions. Distinguish curiosity-driven first use from repeated weekly use. Use aggregate events and voluntary interviews; message bodies are unnecessary for ordinary product analytics.

Ask whether Maya preserved decisions, missed disagreements, assigned work correctly and reduced manual transcription. Review rejected tasks and abandoned proposals alongside successful ones. Product success requires meaningful work created and understandable conversations; a large number of AI invocations alone is not a success metric.

## 4. External primary sources

These sources informed specific decisions; they do not validate FortyOne's implementation, provider account configuration or production capacity. Limits and product APIs should be refreshed when implementing.

| Source                                                                                                                                                                                            | Supported observation                                                                                  | Application in this plan                                                                                |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------- |
| [Redis Pub/Sub](https://redis.io/docs/latest/develop/use-cases/pub-sub/)                                                                                                                          | Pub/Sub delivery is not durable replay for disconnected consumers.                                     | PostgreSQL events and cursor sync recover state; Redis only accelerates notification.                   |
| [PostgreSQL sequence functions](https://www.postgresql.org/docs/18/functions-sequence.html)                                                                                                       | Sequence allocation has rollback/ordering properties unsuitable for assuming transaction commit order. | Serialize durable order within a conversation transaction.                                              |
| [PostgreSQL SELECT locking](https://www.postgresql.org/docs/18/sql-select.html)                                                                                                                   | `SKIP LOCKED` is useful for queue-style consumers, not consistent general reads.                       | Fenced claims for workers; consistent snapshots for history/sync.                                       |
| [PostgreSQL text-search indexes](https://www.postgresql.org/docs/18/textsearch-indexes.html)                                                                                                      | GIN is the preferred index type for text search.                                                       | Start with scoped PostgreSQL full-text search before adding another search platform.                    |
| [MDN SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events), [HTML SSE specification](https://html.spec.whatwg.org/multipage/server-sent-events.html) | SSE framing, connection/reconnection and event-ID behaviour require an application protocol.           | Reuse SSE with explicit multi-conversation cursors, buffering checks and bounded reconnect.             |
| [AWS load balancer attributes](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-load-balancer-attributes.html)                                                            | Idle timeout is configurable and matters for long-lived connections.                                   | Test the actual deployment path and heartbeat interval rather than assuming defaults.                   |
| [Expo push delivery](https://docs.expo.dev/push-notifications/sending-notifications/)                                                                                                             | Tickets and receipts require reconciliation; successful handoff is not proof of device receipt.        | Per-device attempts, receipt polling, finite TTL, rate control and honest delivery metrics.             |
| [OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling#strict-mode)                                                                                             | Strict schemas constrain tool argument shape.                                                          | Closed structured proposals plus independent server authorisation and domain validation.                |
| [OpenAI evaluation guidance](https://developers.openai.com/api/docs/guides/evaluation-best-practices), [trace grading](https://developers.openai.com/api/docs/guides/trace-grading)               | Task-specific evaluations and workflow-level review reveal different failure modes.                    | Versioned held-out cases, human-calibrated grading and action-recovery evaluations.                     |
| [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data)                                                                                                                   | Storage, monitoring, caching and endpoint eligibility have distinct controls.                          | Minimise context, keep explicit storage settings, validate actual account policy and deletion paths.    |
| [OpenAI background mode](https://developers.openai.com/api/docs/guides/background)                                                                                                                | Provider-managed asynchronous work has its own lifecycle/storage behaviour.                            | Optional provider execution mode; the application still owns durable runs and receipts.                 |
| [OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)                                                                                                             | Cache economics and retention depend on model/configuration.                                           | Stable prefixes where useful, measured costs and no authorisation-by-cache shortcut.                    |
| [OWASP prompt-injection prevention](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)                                                              | Untrusted content can redirect an agent; layered controls are necessary.                               | Separate evidence from trusted instructions, restrict tools, gate mutations and test adversarial cases. |
| [WAI feed pattern](https://www.w3.org/WAI/ARIA/apg/patterns/feed/), [ARIA log semantics](https://www.w3.org/TR/wai-aria-1.2/#log)                                                                 | Dynamic feed/log semantics affect focus and announcements.                                             | Validate virtualisation and screen-reader interaction with real assistive technology.                   |

Do not copy platform-specific guidance indiscriminately. For example, Slack agent configuration is not FortyOne's membership model, a provider background job is not a database transaction, and a schema-valid tool call is not an authorised user action.

## 5. Architecture decisions

| Decision               | Recommended choice                                               | Alternative and revisit trigger                                                                                                                             |
| ---------------------- | ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Domain/storage         | New chat module and normalized PostgreSQL messages/events.       | Personal transcript blobs, comment reuse and CRDT storage do not meet the same multi-user contract.                                                         |
| Initial transport      | HTTP commands plus upgraded shared SSE and canonical sync.       | WebSocket if a real native/latency/bidirectional constraint is demonstrated. A transport change retains the same durable protocol.                          |
| Live durability        | Transactional outbox, per-room event order and replay.           | Redis-only delivery is insufficient. Larger streaming infrastructure requires measured operational need.                                                    |
| Agent identity         | Existing Maya system actor, projected in team members.           | A fake human account creates billing, permissions, presence and lifecycle errors.                                                                           |
| Agent runtime          | Durable Go orchestration with scoped messaging capabilities.     | Request-only runtime cannot reliably survive client/server restarts; an external workflow engine can be reconsidered if operational complexity warrants it. |
| Context                | Exact selection plus requester/destination-compatible resources. | Whole-workspace stuffing increases cost, noise and disclosure risk without guaranteeing better answers.                                                     |
| Native actions         | Direct bounded explicit creation; review/clarify elsewhere.      | Review every native action is simpler but adds friction; unrestricted autonomy lacks an adequate action contract.                                           |
| Search                 | PostgreSQL full-text search first.                               | Semantic retrieval only after source/deletion/access controls and measured relevance need.                                                                  |
| Shared answers         | Thread reply with compact root status/result.                    | Long root-stream bot output overwhelms human conversation.                                                                                                  |
| Notifications          | Attention-driven, grouped, preference-aware delivery.            | Every-message alerts undermine the chat experience and existing weekly email policy.                                                                        |
| Offline                | Honest draft-only pilot, then real durable outbox.               | Simulated optimistic success without persistent operation identity loses or duplicates work.                                                                |
| Native feature rollout | Independent flags and real-device qualification.                 | Treating hosted web success as native proof misses lifecycle, bridge and notification failures.                                                             |

These are recommendations ready to turn into short repository ADRs during F1/F2. They are not irreversible choices or claims that the new systems exist.

## 7. Implementation handoff

Begin with F1 contracts and F2 transport/native spike while evaluation authors build the initial corpus. Convert settled decisions into repository ADRs, publish typed API/event fixtures, and make one reliable two-user conversation work through the actual authentication path. That vertical slice should prove durable send, replay, current membership, independent thread read state and a real native deep link before expanding feature breadth.

For each later package, keep an evidence row linking the implementation change, tests, staging measurement and production canary. Any change to a shared assumption must update the product, backend, Maya, client and operations chapters together. In particular, direct-action policy, read semantics, retention and notification defaults must have one agreed meaning across all surfaces.
